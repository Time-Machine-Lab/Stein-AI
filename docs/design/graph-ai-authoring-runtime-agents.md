# Graph AI 编排改用运行时智能体：设计提案

状态：设计提案，**尚未实现**。日期：2026-10-14。代码基线：`d9ad07260`（v0.1.4）。关联文档：[V2 使用与发布说明](../graph-v2-delivery.md)、[V2 wire contract](graph-v2-contract.md)、实施计划与待办 [2026-10-14-graph-ai-authoring-runtime-agents](../plans/2026-10-14-graph-ai-authoring-runtime-agents.md)。

## 1 背景

Graph 的目的是用程序可靠地编排**多个智能体组成的团队**：谁做哪一步、结果怎么交接、何时等人。引擎层（分支、并行、汇合、循环、子图、审批、按节点绑定智能体）已经按这个目标实现。

但“AI 创建工作流”这个入口偏离了目标。线上 v0.1.4 页面显示“服务器尚未配置 AI 生成功能”，所选“执行智能体”也不参与生成。本文记录已核实的偏差、给出改法，并列出需要产品负责人拍板的问题。

## 3 目标与非目标

目标：

1. 生成工作流不再需要服务端模型密钥，由用户选择的运行时智能体完成，与产品里其他“智能体生成资产”的功能一致。
2. 生成时模型能看到可用的团队成员，并为每个节点选择合适的智能体，用户可以限定范围、可以在草稿中逐个修改。
3. 保持现有契约：生成只产生**可编辑草稿**，不运行、不发布、不审批；输出必须通过现有定义校验；审批人仍由用户指定。

非目标：

- 不改 Graph 引擎、节点类型和 V2 定义格式。
- 不让生成过程自动启动或发布流程。
- 不在本期解决安全与护栏类遗留问题（见计划文档的待办）。

## 4 方案

### 4.1 复用已有的“智能体任务”模式

仓库里已有同构先例：快速创建任务（`quick_create_prompt`）。服务端为所选智能体入队一个带专用提示词的任务，daemon 在运行时里执行，智能体通过 `multica issue create` 提交产物，完成后服务端通知用户。Graph 生成采用同样的形态：

1. 服务端入队“Graph 编排任务”，携带用户描述、对话历史、当前定义、可用智能体目录。
2. daemon 构造专用提示词（新增类似 `buildQuickCreatePrompt` 的构造函数），智能体按契约产出 V2 定义 JSON。
3. 智能体通过 CLI 提交草稿（见 4.4），服务端校验后关联到该次生成。
4. 前端收到完成事件后展示提案，用户选择应用或丢弃，行为与现在一致。

### 4.2 团队目录

生成任务的上下文新增“可用智能体目录”，每项包含：别名（`agent_1`…，不暴露 UUID 给模型的原则保持不变）、名称、描述或角色说明、运行时类型与在线状态、已启用技能名称。

筛选规则：只列出当前用户有权调用（沿用 `canInvokeAgent`）、未归档、属于当前工作区的智能体；不包含凭据、环境变量、MCP 配置、指令全文。目录大小有上限，超出时按用户选择的范围和最近使用排序截断，并在提示词里说明“目录已截断”。

### 4.3 选择语义

把单个 `agent_id` 换成：

- `agent_scope`：可选，限定生成可使用的智能体集合；为空表示全部可调用智能体。
- `default_agent_id`：可选，模型没有明确理由时使用的默认执行者。

服务端在接受草稿前校验：每个节点的 `agent_id` 必须在 `agent_scope`（或默认全集）内、可调用、未归档。越界一律拒绝并让智能体重试，不静默替换。节点的最终执行者仍在发布时由 `PrepareNode` 冻结快照，这一步不变。

前端把“执行智能体”下拉框改为“参与的智能体”多选加“默认执行者”。草稿中每个节点的智能体可单独更换（引擎和编辑器已支持）。

### 4.4 草稿的提交与校验

方案一（推荐）：新增 CLI 子命令，例如 `multica graph draft submit --generation <id> --file draft.json`，沿用 quick-create 的“智能体调用 CLI 提交”形态。服务端执行与现在相同的校验链：规范化、`graphTransformActors`、`graph.ValidateDefinition`，不通过时把具体错误返回给智能体，由它在同一任务内修正，最多重试 N 次。

方案二：让智能体把 JSON 作为任务最终输出，服务端从结果里解析。实现更简单，但失败反馈要靠新开任务，体验差。

需确认：`server/cmd/multica/cmd_graph.go` 目前已有哪些子命令，能否直接承载 `draft submit`；若新增，需要同步更新内置 Skill 与其 source-map（见 4.7）。

### 4.5 异步化

现在的接口是同步的：请求等模型返回。改为任务后必须异步：

- `POST /api/graphs/generations` 返回 `202` 与 `generation_id`，同时记录用户、工作区、选定范围、任务 ID。
- `GET /api/graphs/generations/{id}` 返回状态：`queued`、`running`、`succeeded`、`failed`、`cancelled`，成功时带 `definition`。
- 状态变化通过 WebSocket 事件使 Query 缓存失效，前端不在 Zustand 里镜像服务端数据（遵守仓库的状态规则）。
- 支持取消；daemon 离线或超时给出明确错误并允许改选其他智能体重试。
- 每用户同时只允许一个进行中的生成，沿用现有的并发限制思路。
- 草稿是否持久化：见第 6 节问题 3。

### 4.6 现有服务端 LLM 路径的处理

三个选项：

- A：运行时路径稳定后删除服务端 LLM 路径（仓库约定：产品内部不保留并行旧路径）。
- B：保留为后备，仅当用户没有选择任何智能体时使用。
- C：长期双轨。

建议 A，但因 v0.1.4 已上线，先 B 过渡：运行时路径通过验收后再删除。该决定见第 6 节问题 2。

### 4.7 安全与合规

- 生成任务的提示词必须声明“只产出草稿，不执行、不发布、不审批”，用户描述与当前定义都视为不可信输入（沿用现有提示词的措辞）。
- 运行时智能体有工具能力，这与服务端 LLM 调用不同：它在该用户机器上运行。生成任务使用空的专用工作目录，不挂载仓库；服务端**只信任通过校验的提交结果**，智能体在任务里做的其他事情不影响草稿。
- 这不是沙箱。智能体仍然拥有它平时的权限，所以生成应只在用户明确选择的、有权调用的智能体上进行，并在界面上说明“将消耗该智能体的额度并占用一个运行时”。
- 按仓库规则：新增或修改 CLI 命令后，同一个 PR 更新 `server/internal/service/builtin_skills/*` 下相关的 `SKILL.md` 与 `references/*-source-map.md`；新增接口需要 zod schema 加畸形响应测试；数据库不加外键、索引用 `CONCURRENTLY`。

## 5 验收标准

1. 未配置任何 `MULTICA_LLM_*` 的环境里，选择在线智能体后能生成草稿。
2. 同一次生成里，不同节点可以使用不同智能体；越界智能体被服务端拒绝。
3. 生成模型的上下文不包含智能体 UUID、凭据、环境变量与指令全文（用测试断言发送内容）。
4. 生成期间取消、daemon 离线、超时、模型输出非法并重试耗尽，都有明确状态且不留下半成品草稿。
5. 草稿应用后走现有“保存、校验、发布”流程，发布与运行行为不变。
6. 用真实 Codex 与 Claude 各端到端跑一次，记录证据（沿用 V2 验收的做法）。

## 6 需要产品负责人拍板的问题

1. **选择语义**：用“多选范围加默认执行者”，还是“只选一个默认执行者，由模型在全部可调用智能体里分配”？前者可控，后者省事。
2. **旧路径**：按 4.6 选 A、B 或 C？
3. **草稿持久化**：生成结果只保存在任务结果里（随任务清理），还是单独建表保留历史？后者需要新增迁移。
4. **成本归属**：生成消耗所选智能体所有者的额度，是否可接受？是否需要在生成前提示？
5. **运行时选择（D7）**：多智能体团队的成员分布在不同运行时上，当前启动入口是否满足，需要先核实再决定是否纳入本期。
6. **其他偏差（D8）**：使用中发现的其他问题请补充到偏差清单。
